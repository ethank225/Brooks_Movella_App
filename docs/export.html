Deep Dive: Export Pipeline

Three-queue architecture, BLE transfer, watchdogs, and retry logic.

ExportManager (Managers/ExportManager.swift, ExportManager+BLETransfer.swift, ExportManager+Persistence.swift) manages the full export lifecycle with three private queues plus the shared sdkQueue.

Queue Architecture

QueuePurpose
sdkQueue (shared from DotManager) All SDK device calls + receives BLE packet callbacks
fileQueue (serial, .userInitiated) CSV file I/O — open, write batches, close handles
exportSequenceQueue (serial, .userInitiated) Waits on semaphore for all devices to complete

Export Flow

Guards: fetchRecordings, startExport, and retryFailed all check DotManager.shared.isBusy — export is blocked during sync and recording. isTransferring writes are wrapped in setOnMain for thread safety.

fetchRecordings(for: dots)
    └─ For each dot (DispatchGroup):
        dot.getExportFileInfo → recordings[dot.address] = files
    └─ group.notify(queue: .main):
        exportPhase = .ready

buildCart()
    └─ Selected files → CartItems with auto-session grouping (20min window)

startExport()
    └─ Create ExportTasks from CartItems
    └─ Group tasks by dot address
    └─ For each dot (concurrent):
        exportFilesForDot(dot, tasks) → semaphore.signal()
    └─ exportSequenceQueue.async:
        for _ in 0..<deviceCount: semaphore.wait()
        → exportPhase = .done

Per-File BLE Transfer (exportFilesForDot)

For each file within a dot, files are exported sequentially:

1. fileQueue.async:
      Create CSV file, write header, open FileHandle

2. sdkQueue.async:
      device.stopExportFileData()        // reset prior state
      device.exportDataFormat = Data(...) // timestamp, euler, accel, angvel
      device.recording.exportFileList = [fileIndex]

      // Install packet callback (fires on sdkQueue)
      device.setDidParseExportFileDataBlock { plotData in
          watchdog.beat()                 // reset stall timer
          Format CSV row from plotData fields
          Append to batch buffer
          if packetsReceived % 200 == 0:
              let captured = batch
              fileQueue.async { fileHandle.write(captured) }
          Update progress every 100 packets or 0.5s
      }

      // Install done callback (fires on sdkQueue)
      device.recording.exportFileDone = { ... in
          doneFired = true
          // Watchdog will handle finalization
      }

      // Install watchdog (10s stall detection)
      ExportWatchdog(timeout: 10, queue: sdkQueue) {
          if doneFired:
              Flush final batch → validate → success or fail
          else:
              Genuine stall → fail, delete partial CSV
      }

      device.startExportFileData()       // begin BLE transfer

Generation IDs

exportFileGenerations: [String: Int] (keyed by dot address) guards against stale SDK callbacks:

// Before each file export:
exportFileGenerations[dot.address, default: 0] += 1
let generation = exportFileGenerations[dot.address, default: 0]

// Inside every callback:
guard exportFileGenerations[dot.address] == generation else { return }

Bumped on: export start, cancel, watchdog timeout. If a callback from a prior attempt fires after the generation was bumped, the guard rejects it.

Watchdog

ExportWatchdog runs a DispatchSourceTimer on sdkQueue, firing every 1 second. It checks Date().timeIntervalSince(lastPacketAt) > timeout. The packet callback calls watchdog.beat() to reset lastPacketAt.

On timeout, the watchdog handles two cases:

  • doneFired == true: The SDK signaled completion but the stream was still draining. Flush the final batch, validate packet continuity, and mark success or fail.
  • doneFired == false: Genuine stall (no packets for 10+ seconds). Stop the export, delete the partial CSV, mark failed.

Packet Count Validation

After each file completes, validatePacketCount(csvURL:) reads the CSV, extracts the packet_counter column, and checks that (lastCounter - firstCounter + 1) == rowCount. Any gap means BLE packets were lost. Failed validation marks the task with hasPacketLoss = true and status .failed.

Progress Estimation

SDK provides no total packet count. Estimated from file size:

let estimatedDuration = max(Double(fileSize) / (88.0 * 33.0), 1.0)
// ~88 bytes per on-device packet, ~33 packets per second over BLE
let progress = min(elapsedTime / estimatedDuration, 0.99)

Progress caps at 0.99 until exportFileDone fires, then jumps to 1.0.

Cancel Flow

cancelExport() must unwind all concurrent state:

  1. Bump exportSequenceGeneration (makes the sequence completion handler a no-op)
  2. Bump all per-file exportFileGenerations (makes packet/done callbacks no-ops)
  3. Stop all watchdogs
  4. Close all file handles on fileQueue
  5. Call device.stopExportFileData() on sdkQueue for all actively-transferring dots
  6. Mark all running/queued tasks as .canceled, delete partial CSVs
  7. Signal the semaphore for each pending device (unblocks exportSequenceQueue)

Retry Logic

retryFailed() inspects disk state before deciding what to re-export:

  • If CSV exists and wasn't marked with packet loss → mark success (already done)
  • If CSV exists but has packet loss → delete CSV, re-export from scratch
  • If no CSV exists → full BLE re-export

There is no partial resume — the streaming pipeline has no intermediate binary format to resume from.

Semaphore timeout: All semaphore.wait() calls in retry paths use a 5-minute timeout (.now() + 300). If a BLE transfer callback never fires (e.g. sensor disconnected mid-transfer), the semaphore unblocks and the task is marked failed instead of hanging the export queue forever.

On retry, retried files are placed into the same session folder as the original export. The folder is matched by reading the Session ID from metadata.csv via resolveSessionFolder(baseName:sessionId:in:).

Persistence

Tasks are saved to Application Support/export_records.json whenever status changes to .success, .failed, or .canceled. On next app launch, restorePersistedTasks() rehydrates tasks, verifies CSV files still exist on disk, and deletes orphaned partial CSVs from the ExportCache directory. A fallback read checks the old Documents/export_records.json path for upgrades from prior versions.

Session Metadata

Before export starts, CartView captures run details into a SessionMetadata struct and sets it on ExportManager.sessionMetadata:

struct SessionMetadata: Codable {
    let runnerName: String
    let shoeBrand: String
    let shoeModel: String
    let shoeGeneration: String
    let conditionType: String
    let study: String
    let test: String
    let product: String
    let outputRate: Int      // from DotManager.selectedOutputRate
    let filterIndex: Int     // from DotManager.selectedFilterIndex
}

This metadata is also persisted into the ExportContext (stored in UserDefaults) for crash recovery. If the app restarts mid-export, restoreExportContextIfNeeded() restores it.

Post-Export Organization

After all BLE transfers complete, finalizeExport(generation:) orchestrates session folder creation:

finalizeExport(generation:)
    └─ DispatchQueue.main.async:
        Snapshot @Published task data (status, outputURL) → [TaskMoveInfo]
        Capture sessionMetadata
    └─ fileQueue.async:
        organizeIntoSessionFolders(snapshot:, metadata:)
            └─ Group tasks by sessionId
            └─ For each session:
                resolveSessionFolder() — reuses existing folder if Session ID matches
                Create directory (if new)
                Write metadata.csv (includes Session ID)
                safeCopy each CSV from ExportCache/ → session folder
            └─ Set exportedSessionFolderURLs
    └─ DispatchQueue.main.async:
        exportPhase = .done
        persistTasks()
        sendCompletionNotification()

Threading contract

@Published properties on ExportTask (status, outputURL) must be read on the main thread. The snapshotSuccessTasks() method captures this data into plain TaskMoveInfo structs before dispatching to fileQueue. File operations only use the snapshot, never the live task objects.

Copy, not move

CSVs are copied (not moved) from ExportCache into session folders. The original flat CSV stays in place so Supabase uploads (which fire per-task during BLE transfer via onTaskCompleted) can read from the stable path. Originals are cleaned up when the user taps “Clear & Start Over”.

Collision handling

Folder names are resolved by resolveSessionFolder(baseName:sessionId:in:). If a folder with the target name exists and its metadata.csv contains the same Session ID, the folder is reused (retry case). Otherwise, _1, _2 suffixes are tried until a non-existent or matching folder is found. This prevents duplicate folders when retrying failed exports.

safeCopy() checks FileManager.fileExists(atPath:) at the target path before calling copyItem. If a file with the same name already exists, it appends the first 6 characters of the task ID to the filename stem.

Session Folder Structure

2026-03-22_17-30-00/
  metadata.csv          ← key-value pairs
  Heel_file0.csv        ← from CartItem.label (includes sensor display name)
  Shank_file1.csv

The folder name comes from the earliest recording timestamp in the session group, formatted as yyyy-MM-dd_HH-mm-ss. If a folder with that name already exists and belongs to a different session, a _1, _2 suffix is appended. If it belongs to the same session (matched by Session ID in metadata.csv), the existing folder is reused.

Share Packaging

The share button in ExportResultsSection calls packageForSharing(), which creates a single shareable bundle:

packageForSharing() → URL?
    └─ Create tmp/BrooksExport_yyyy-MM-dd/
    └─ Copy each session folder from Documents/Exports/ into it
    └─ Return the top-level directory URL

Result:
  tmp/BrooksExport_2026-03-22/
    2026-03-22_17-30-00/
      metadata.csv
      Heel_file0.csv
      Shank_file1.csv
    2026-03-22_17-45-00/
      metadata.csv
      ...

This single URL is passed to UIActivityViewController. AirDrop sends the entire folder hierarchy. A fallback path shares individual file URLs if packaging fails.

A hint below the share button reads “Files also saved to Files → Exports” so users know the persistent copy exists.
