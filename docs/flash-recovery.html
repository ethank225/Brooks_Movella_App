Flash Recovery System

Detecting and recovering from corrupted flash storage on Movella DOT sensors.

Background

A single change — sorting connected dots alphabetically in DotRegistry — introduced a race condition in the connection queue. When the SDK auto-reconnected sensors in a different order than the queue expected, it attempted to connect already-connected sensors. This corrupted the BLE state, and if the sensor was performing a flash operation at the time, the flash storage index was left in an inconsistent state (the SDK reports XSFlashInfoIsUninitialized and getFlashInfo returns 0/0).

A second corruption path was discovered through testing: killing the app mid-erase. The sensor firmware continues erasing after BLE disconnect, but the app has no record of the ongoing operation on next launch.

Root Causes and Fixes

Race condition in connection queue

Sorting dots alphabetically changed the queue order, but the SDK reconnects in whatever order Bluetooth responds. Device B could connect while Device A was connectInProgress, causing advanceConnectQueue to clear A's slot. This left connectInProgress stuck and could corrupt BLE state during flash operations.

Fix: advanceConnectQueue(expect:) only clears connectInProgress if it matches the expected device UUID. Eliminates double-connects entirely.

App killed mid-erase

Cannot be prevented — iOS allows force-kill at any time. The sensor firmware continues erasing independently. On next connect, the app sees 0/0 flash and no record of an ongoing erase.

Fix: Detect mid-erase via recordingStatus == .isErasing, poll until complete.

Detection Layers

Flash issues are detected at five points. Each covers a different timing scenario:

  1. checkSensorActivity (Dot.swift) — On connect, checks recordingStatus before any flash query. If .isErasing, skips flash query and starts polling. If .isRecording, skips flash query and goes straight to .ready. Fastest path.
  2. getFlashInfo callback (Dot.swift) — If the SDK responds with 0/0 or .isUninitialized, checks recordingStatus. If .isErasing, starts polling. If not, marks flashCorrupted.
  3. refreshStorage timeout (DotManager.swift) — If getFlashInfo times out after 5s (SDK won't respond during erase), checks recordingStatus as fallback. If .isErasing, starts polling instead of marking failed.
  4. Flash timeout with active recording (DotManager.swift) — When getFlashInfo times out and recordingStatus shows .isRecording, the sensor is recovered to .ready with restoreRecordingPhase. This handles the app-relaunch scenario where checkSensorActivity missed the recording state because the SDK was too slow to populate the property on a fresh connection.
  5. Erase poll limit (Dot.swift) — After 60 polls (3 minutes), gives up and marks flashCorrupted. Safety net for stuck erases. Note: large flash contents may legitimately take longer; once marked corrupted there is no automatic recovery. See Vulnerabilities & Known Limitations #4.

Two States

isErasingFromPreviousSession: Sensor is mid-erase from a previous session. Firmware is still working. App polls recordingStatus every 3 seconds until erase completes, then reads flash info. No user action needed.

flashCorrupted: Flash is truly corrupted and sensor is not erasing. User must erase to recover. Recording and export blocked globally while any sensor has a flash issue.

UI Components

Each flash state has a dedicated row component in Views/Components/DeviceRows/ that replaces the normal sensor row:

StateComponentVisual
isErasingFromPreviousSession ErasingSensorRow Clock icon + “Finishing erase from previous session” + pink shimmer bar. Pink breathing background.
User-initiated erase ClearingSensorRow Pulsing red trash icon + “Clearing flash storage” + red shimmer bar. Pink breathing background.
flashCorrupted CorruptedSensorRow Orange warning icon + “Storage corrupted” + Erase button. Orange background.

ObservedDotContent (ConnectionView.swift) wraps the Dot with @ObservedObject so the row reacts automatically when isErasingFromPreviousSession, flashCorrupted, or isErasing change. Background color, canErase, and the row variant switch all live inside this sub-view and update without needing DotManager.notify().

Status banners on the Record and Export tabs (ErasingBanner, FlashIssueBanner in Views/Components/Shared/StatusBanners.swift) read from DotManager.hasFlashIssue / isAnyErasingFromPreviousSession, which depend on the connectedDots snapshot. These update via the onEraseStateChanged callback (see below).

Polling Mechanism

When mid-erase is detected, startErasePoll() runs on sdkQueue:

  • Every 3 seconds: calls getRecordingStatus(), waits 0.5s, reads recordingStatus
  • Still .isErasing → schedule next poll
  • No longer .isErasing → erase done, call getFlashInfo for real values, clear flag
  • After 60 polls (3 min) → give up, mark flashCorrupted

Typical erase takes ~42 seconds (~14 polls).

Scanning Suppression

Bluetooth scanning is suppressed while any sensor has isErasingFromPreviousSession == true. Without this guard, the 1-second auto-retry scan timer in ConnectionView can trigger SDK-internal reconnects during polling. A reconnect clears the erase flags in onDeviceConnectSucceeded, then initializeAfterConnect detects the erase again and restarts polling — creating an infinite loop.

The guard lives in DotManager.startScan() via DotRegistry.hasErasingFromPreviousSession. All scan triggers (timer, pull-to-refresh, manual button) flow through startScan(), so a single check blocks them all. Scanning resumes automatically on the next timer tick after the flag clears.

Post-Stop Settle Delay

When a recording that was resumed from a previous app session is stopped, the SDK does not respond to getFlashInfo immediately. The sensor firmware needs time to finalize the flash storage index after the stop. Without a delay, getFlashInfo times out repeatedly — blocking the export page from fetching recordings and preventing new recordings from starting.

DotManager.endSession() waits 2 seconds after all sensors confirm stopped before calling getFlashInfo. This matches the existing settle delay pattern used after Bluetooth-reset reconnects in initializeAfterConnect.

State Change Callback

Dot.onEraseStateChanged is a closure set by DotManager in all three connection paths (onDeviceConnectSucceeded). It fires on the main thread when isErasingFromPreviousSession is set to true or cleared (poll success and poll timeout). The callback calls DotManager.notify() on stateQueue, which re-pushes the connectedDots snapshot. This causes the Record and Export tabs to re-evaluate hasFlashIssue and update their banners.

The Connect tab does not need this callback — it uses ObservedDotContent with @ObservedObject to react directly to the Dot’s @Published properties.

Connection Reset

On every new connection, all flags reset before initializeAfterConnect:

  • isErasing = false
  • isErasingFromPreviousSession = false
  • flashCorrupted = false

Detection logic determines real state from hardware. No stale values carry over.
