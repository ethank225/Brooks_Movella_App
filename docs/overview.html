Overview & Concepts

Reference guide for the core concepts, patterns, and design decisions.

Sensor Basics (Movella DOT)

  • Each DOT has a 3D accelerometer, gyroscope, and magnetometer
  • Communicates via Bluetooth Low Energy (BLE) 5.0
  • Has 64MB internal storage, records up to 6 hours at 60Hz
  • Supports output rates from 1Hz to 120Hz (120Hz recording only)
  • Internal sampling rate is 800Hz, downsampled via Strapdown Integration (SDI)
  • Sensor fusion algorithm (XKFCore) runs on-device, outputs drift-free 3D orientation
  • Each sensor has its own clock domain — synchronization is required for multi-sensor setups

Synchronization

  • Sync aligns sensor clocks to a common time base via BLE advertisement messages
  • One sensor is the root node, others are scanners
  • Sync takes ~15 seconds and the SDK disconnects/reconnects sensors during the process
  • Sync accuracy: 1 ppm after 30 min, 4 ppm after 1 hour
  • After sync, multiple recordings can be started/stopped without re-syncing
  • Sync is purely clock alignment — sensors do NOT need to be on a flat surface. Movella recommends syncing on a table for body-mounted scenarios because BLE proximity (<50cm) improves sync success rate during the disconnect/reconnect phase — not because the algorithm requires a flat surface.
  • Best practice: keep sensors and phone within 50cm during sync, don't stack sensors
  • The SDK cannot handle two concurrent startSync calls. If Runner A is syncing, Runner B must wait.
  • Sync persists on the sensor until powered off, factory reset, or stopSync is called

Threading Model (DotManager)

  • stateQueue (serial) — protects DotRegistry mutations and internal flags. All state reads/writes happen here.
  • sdkQueue (serial) — serializes all Movella SDK API calls. SDK is not thread-safe.
  • Main thread — all @Published property writes for SwiftUI
  • Pattern: SDK callback fires on arbitrary thread → hop to stateQueue for state mutation → snapshot to main for UI
  • Never synchronously dispatch from stateQueue to sdkQueue or vice versa — deadlock risk

Busy State Hierarchy

DotManager exposes several busy flags at different levels. Understanding which flag gates which operation is critical:

DotManager.isBusy (UI gate — blocks export, erase, connect, scan)
├─ isAnySyncing
│   ├─ runnerPhases contains .syncing
│   └─ resyncingRunners is non-empty
└─ runnerPhases contains .startingRecording / .recording / .stoppingRecording

DotManager.isBusyInternal (stateQueue gate — blocks refreshStorage, flash timers)
├─ registry.syncInProgress (also used for sync-specific reconnect suppression)
└─ runnerPhasesInternal contains active phases

DotManager.isErasing (derived from connectedDots — blocks export, recording start)
DotManager.hasFlashIssue (derived — blocks recording start, shows banners)
└─ isAnyErasingFromPreviousSession (subset — distinguishes "finishing erase" from "corrupted")

isBusy reads published state on main thread and is the primary UI gate. isBusyInternal reads runnerPhasesInternal on stateQueue and gates internal operations like refreshStorage that shouldn't run during active sessions.

Connection Lifecycle

  • Phases: idle → connecting → initializing → ready
  • After BLE connect succeeds, the sensor needs initialization (getFlashInfo for storage info)
  • getFlashInfo will NOT respond if the sensor is currently recording — this times out and causes "initialization failed"
  • Fix: before calling refreshStorage/getFlashInfo, query recording status with checkSensorActivity(completion:) which uses three racing paths (see Connections docs). If recording, skip flash query and go straight to .ready
  • refreshRecordingStatus() is async with two queue hops (sdkQueue → SDK callback → main) — checking isRecording immediately after calling it will see stale data. Always use the callback-based checkSensorActivity instead.
  • Battery and flash data are unavailable on the fast recording reconnect path (getFlashInfo won't respond during recording). The UI shows a hatched bar with “—” until data becomes available after recording stops.
  • The SDK fires disconnect/reconnect events during sync — suppress these when syncingUuids contains the device UUID, not based on a global sync flag.
  • Flash timeout recovery: if getFlashInfo times out and recordingStatus == .isRecording, the sensor recovers to .ready with recording phase restoration instead of failing initialization. See Connections.
  • Battery on fast path: Battery is NOT read on the fast recording reconnect path — reused SDK device objects return stale 0 values. The pre-disconnect battery value is preserved by the Dot model.
  • See Flash Recovery for how flash corruption and mid-erase states are detected and recovered during initialization.

Recording

  • Recording stores data on-sensor internal flash, not streamed over BLE
  • Recording starts/stops via SDK commands
  • 0xFFFF = record indefinitely until explicitly stopped
  • Sensor continues recording even if BLE disconnects or app is killed
  • On reconnect, device.recording.recordingStatus from the SDK is the source of truth for recording state
  • dot.isRecording is @Published private(set) — only writable from within Dot via syncRecordingState(). This single method reads device.recording.recordingStatus (the live SDK stored property) and pushes the result to @Published on main thread. All recording state updates — SDK callbacks, polling success, idle-sensor skip paths — go through this one method. The private(set) makes any external write a compile error.
  • waitForRecordingState polls device.recording.recordingStatus on sdkQueue every 0.3s. On success, calls syncRecordingState() on main thread before the completion handler, ensuring the UI flag is updated before the runner phase transition.
  • performStopRecording checks the live SDK property device.recording.recordingStatus before sending stop — if a sensor is already idle (e.g. power-cycled during recording), the stop is skipped and syncRecordingState() is called on the skip path to sync the UI flag.
  • endSession no longer calls stopSync — sensors stay in measurement mode (synced) after recording stops. Multiple recordings can be started/stopped without re-syncing.
  • No recovery persistence file needed — isRecording + RunnerStore runner assignments restore everything

Sync Status

  • sessionSynced is @Published private(set), updated only through refreshSyncStatus() which reads device.isSynced() on sdkQueue and publishes on main.
  • device.isSynced() is an in-memory flag on the SDK — set to true after successful startSync, never queried from hardware on reconnect.
  • On fresh app launch, isSynced() is always false — user must sync before recording (2+ sensors).
  • Sync and record are independent operations: sync first, then record (two separate user actions). beginSession guards on device.isSynced() for all dots and refuses to record if not synced.
  • resyncRunner(runnerId:) provides standalone re-sync without starting recording. syncSession() is the single-runner convenience wrapper.
  • refreshSyncStatus() is skipped during active sync windows (updateDevice(isSyncing: true)) to avoid misleading intermediate values from the SDK's internal disconnect/reconnect cycle.

Per-Runner Session Management

  • A Runner is a named group of sensor UUIDs (up to 3 dots per runner)
  • Each runner has its own independent SessionPhase tracked in runnerPhasesInternal
  • Sync and recording are separate steps: user must sync first (when 2+ sensors), then start recording. beginSession guards on device.isSynced() and refuses to record unsynced sensors. The UI action button routes to the correct step based on sync status.
  • Multiple runners can record concurrently
  • Runners cannot sync concurrently (SDK limitation) — UI disables start buttons on other runners while one is syncing
  • RunnerStore persists runner assignments to runners.json
  • DotManager.runnerPhases is in-memory only, rebuilt from isRecording + RunnerStore on reconnect
  • A computed aggregateSessionPhase provides backward compatibility for views that don't need per-runner granularity

Per-Runner State Machine

                  +----------------------------------------------------------+
                  |                                                          |
                  v                                                          |
   idle ---> [resync] ---> idle (synced)                                     |
     |            |                |                                         |
     |            +---> error -----+--> [dismiss] ---> idle                  |
     |          ("Sync failed")                                              |
     |                             |                                         |
     +-----------------------------+                                         |
     |                                                                       |
     | guard: isSynced() if 2+ sensors                                       |
     |                                                                       |
     +---> startingRecording ---> recording ---> stoppingRecording ----------+
                  |                                      |
                  +---> error("Failed to start")         +---> error("Failed to stop")
                              |                                      |
                              +---> [dismiss] ---> idle <------------+

Sync is required before recording (2+ sensors). beginSession checks device.isSynced() on every dot and blocks if any is not synced. With 1 sensor, the resync step is skipped. After stoppingRecording, sensors stay synced — can record again without re-sync.

Key constraint: beginSession checks device.isSynced() on every dot. With 2+ sensors, if any dot is not synced, recording is blocked. The UI shows “Sync Sensors” instead of “Start”. The only path to recording with 2+ sensors goes through sync first.

Two UI Modes

  • Solo runner mode (default, SyncView): all connected dots treated as one group. An ephemeral runner with id "__single__" is managed automatically by convenience methods (syncSession(), beginSession(), endSession()). Shows a single sync status indicator and record button for all sensors.
  • Researcher mode (ResearcherModeRecordView): user creates named runners and assigns dots via drag-and-drop from an AvailableDots pool to RunnerCard drop slots. Each runner syncs and records independently. Runners persist across app sessions.
  • Toggled by RunnerStore.isMultiRunnerMode, backed by UserDefaults "multi_runner_mode". DotManager doesn't know about modes — it just operates on runner IDs.

UI Components (Researcher Mode)

  • RunnerCard: Per-runner card with header (status circle, editable name, sync status icon, resync button, trash button), dots row (up to 3 DotChip views + EmptyDotSlot drop targets in equal-width layout), and a dynamic action button that shows Sync/Start/Stop/Retry based on runner phase.
  • AvailableDots: Horizontal scrollable row of unassigned sensors. Each DotChip is fixed-width (100pt) and draggable. The entire row is a drop target for unassigning sensors from runners.
  • DotChip: Sensor display tile showing display name, storage bar with percentage, and connection indicator. Supports drag-and-drop, double-tap to identify, and optional unassign (X) button.
  • EmptyDotSlot: Dashed-border drop target within RunnerCard. Highlights blue when a sensor is dragged over. Does not animate when sensors are added/removed.
  • Resync button and trash icon gray out during sync. The action button is disabled during transitions.

Sensor Naming

  • SensorNameStore maps sensor UUID to user-defined label via UserDefaults "dot_names"
  • Purely visual — all logic uses UUID, display layer substitutes names
  • Falls back to showing UUID if no name is set
  • Editable inline on the ConnectionView

Export

  • Files exported from sensor internal storage via BLE
  • Only query sensors in .ready connection phase — querying during .initializing causes SDK timeouts
  • Keep sensors within arm's length during export for BLE reliability
  • Each sensor needs both calibration file (small) and run file (large) exported
  • Packet loss or upload failure prompts retry

Persistence Summary

  • runners.json — runner assignments (id, label, sensorUuids). Source of truth for which sensors belong to which runner.
  • UserDefaults "multi_runner_mode" — UI mode toggle
  • UserDefaults "dot_names" — sensor UUID to display name mapping
  • No session recovery file — SDK isRecording + runners.json restores state on reconnect

Key Lessons

  • The Movella SDK is not thread-safe. All SDK calls must go through a single serial queue.
  • SDK callbacks fire on arbitrary threads. Always hop to your own serial queue before mutating state.
  • During sync, the SDK disconnects and reconnects sensors internally. Your delegate callbacks must detect this and suppress connection state changes for syncing sensors.
  • getFlashInfo does not respond while a sensor is recording. Always check recording status before querying flash.
  • refreshRecordingStatus() is async — never check isRecording synchronously after calling it.
  • SampleTimeFine is a relative microsecond clock that resets on sensor reboot. It has no relationship to UTC.
  • iOS Bluetooth UUIDs are phone-specific and can theoretically change, but are stable enough for single-phone workflows.
  • The sensor's MAC address (D4:22:CD:xx:xx:xx) is the only truly permanent identifier across devices.
  • The Movella SDK sometimes reuses the same device object (same pointer) after reconnect. Stored properties on reused objects retain stale values from the previous session, and block-based callbacks (updateRecordingStatus, battery updates) are silently broken. Always verify state via fresh BLE reads (getRecordingStatus) or property polling rather than trusting cached properties or callbacks on reconnected devices.
  • Single-writer pattern for isRecording: All recording state updates go through syncRecordingState(), which reads the live SDK property device.recording.recordingStatus and pushes to @Published on main thread. The property is @Published private(set) — any external write is a compile error. SDK callbacks, polling success, and idle-sensor skip paths all funnel through this one method.
  • Single-writer pattern for sessionSynced: Same approach — refreshSyncStatus() reads device.isSynced() on sdkQueue and publishes on main. Skipped during active sync windows (updateDevice(isSyncing: true)) to avoid misleading intermediate values from the SDK's internal disconnect/reconnect cycle.
  • DotManager.isBusy is the single gate for all BLE operations. Views should never independently compute busy state from session phases.
  • Derive state from per-Dot properties when possible (e.g. isErasing computed from connectedDots) instead of manually set/clear flags that can go stale.

Vulnerabilities & Known Limitations

Identified through code audit of the full sensor lifecycle. Grouped by impact.

High Priority

  1. Partial sensor failure escalates to full session error. DotOperationRunner.runAll reports a single success boolean. If 1 of 3 sensors fails startRecording or stopRecording, the entire runner moves to .error. Partially fixed: performStartRecording now aborts the group on first failure (preventing a crash), but the underlying runAll design still uses a single boolean rather than per-sensor results. See DotOperationRunner.
  2. Disconnect during recording only errors when ALL sensors disconnect. onDeviceDisconnected checks hasConnected across the runner — if a 3-sensor runner loses 1 sensor mid-recording, no warning is shown. The runner only moves to .error when the last connected sensor drops.
  3. checkSensorActivity timeout assumes idle. The polling loop trusts .isRecording/.isErasing immediately and only waits 1s for .isIdle, but the 3-second fallback timeout still assumes idle. If BLE is too slow, a recording sensor gets marked idle. The flash timeout recovery path catches most cases, but recording state may not restore until resumeRecordingSession() on next SyncView.onAppear. See Connections for the three-path mechanism.
  4. Erase poll timeout marks sensor as corrupted. After 60 polls (~3 minutes), flashCorrupted = true with no automatic recovery. Large flash contents may legitimately take longer to erase. See Flash Recovery.
  5. BT power-off during sync leaves stale callback risk. onManagerStateUpdate(.poweredOff) calls clearBusyFlags(), resetting syncInProgress and syncingUuids. But performSync’s SDK completion closure may still fire later with captured pre-reset data, potentially re-setting syncInProgress or modifying cleared state. Potential fix: guard at the top of the performSync completion checking if syncingUuids was already cleared. See BT Power-Off Recovery.

Medium Priority

  1. Frozen device references during sync can go stale. syncingUuids prevents device reference updates during sync via recordDiscovery/recordReconnection guards. If the SDK creates a new device object during its internal reconnect, the frozen reference may have outdated properties until sync completes. See Device Reference Freezing.
  2. canResync TOCTOU window. canResync(runnerId:) reads @Published runnerPhases on main thread; resyncRunner re-checks runnerPhasesInternal on stateQueue. Another runner could start syncing between the two checks. Mitigated by guards in resyncRunner, but the UI may briefly show an enabled button that becomes disabled on tap.
  3. Flash settle delay is heuristic (2s). After a BT-reset reconnect, initializeAfterConnect adds a 2-second settle delay before querying flash. If SDK initialization takes longer, getFlashInfo times out with no retry. Results in .failed("Initialization timed out"). See The Settle Delay.
  4. Post-stop flash refresh can race with user actions. endSession uses a 2-second asyncAfter to refresh flash info after recording stops. The isBusyInternal guard helps, but there is a window where the user has already started a new recording and the phase transition hasn't propagated to the guard check.
  5. Single-runner beginSession() main→stateQueue hop. The convenience beginSession() dispatches to main for RunnerStore.setRunner(), then calls beginSession(runnerId:) which re-enters stateQueue. Another stateQueue operation could interleave between the two dispatches.

Lower Priority

  1. Connect timer on main, cancellation on stateQueue. DispatchWorkItem timers run on main thread; cancellation dispatches to stateQueue. If stateQueue is blocked (e.g., during sync), the timeout fires late. Not a correctness issue but delays user feedback.
  2. SDK duplicate callbacks guarded manually everywhere. The hasCapturedResult pattern is repeated in setFlashInfoDoneBlock, exportFileDone, and onDeviceConnectSucceeded without abstraction. Each guard works correctly but the repetition is error-prone.
  3. resumeRecordingSession only checks isRecording. If checkSensorActivity timed out and marked the sensor idle, isRecording will be false. The session won't auto-restore until the user navigates to SyncView (which calls resumeRecordingSession()).
