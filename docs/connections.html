Deep Dive: Connection Queue & Reconnect Logic

Serial connection queue, timeout handling, four reconnection paths, and Bluetooth power-off recovery.

Step-by-Step: User Tap to .ready

The complete chain from “user taps Connect” to “sensor shows as .ready in the UI”. Typical time: ~3 seconds for first connect, ~5 seconds for BT-reset reconnect (includes 2s settle delay).

1. Queue the UUID (stateQueue)

connectByUuid(uuid)
  ├─ connectQueue.append(uuid)
  ├─ connectionPhase = .connecting          // UI shows "Connecting..."
  ├─ startScan()                            // BLE scan begins
  ├─ startConnectTimer(uuid)                // 10-second timeout
  └─ processConnectQueue()                   // dequeue and connect

2. Dequeue and issue SDK connect (stateQueue → sdkQueue)

processConnectQueue()
  ├─ dequeueNextConnection()
  │     guard: connectInProgress == nil         // one at a time
  │     guard: !syncInProgress                  // blocked during sync
  │     └─ connectInProgress = uuid
  └─ sdkQueue: DotConnectionManager.connect(device)

3. SDK connect succeeds (SDK thread → stateQueue)

onDeviceConnectSucceeded(device)
  ├─ cancelConnectTimer(uuid)
  ├─ recordConnection(device)               // creates Dot if first time
  │     connectionPhase = .initializing          // UI shows "Initializing..."
  ├─ sdkQueue: DotDevicePool.bindDevice(device)
  ├─ resetEraseState(dot)                   // clear erase flags
  ├─ advanceConnectQueue()                  // start next device
  └─ initializeAfterConnect(dot, settleDelay)

4. Check sensor activity (sdkQueue, ~0.3–3s)

checkSensorActivity { activity in ... }
  Three racing paths (first wins):
  ├─ One-shot callback (~0.3s)              // fastest, new device objects
  ├─ Property polling every 0.3s (~0.6s)    // catches reused objects
  └─ 3-second timeout                       // assumes idle

5. Branch on result (stateQueue)

if .idle:
  └─ refreshStorage(dot, settleDelay)       // query flash → step 6

if .recording:
  ├─ connectionPhase = .ready               // skip flash query
  ├─ refreshSyncStatus()
  └─ restore runner phase to .recording      // DONE

if .erasing:
  ├─ connectionPhase = .ready
  ├─ isErasingFromPreviousSession = true
  └─ startErasePollFromManager()             // DONE (polls until complete)

6. Flash storage query (sdkQueue, ~0.5–1s)

refreshStorage()
  ├─ waitForInitialization (poll every 0.2s, 5s timeout)
  │     if settleDelay: wait extra 2s after isInitialized == true
  └─ getFlashInfo()
      ├─ SDK callback: used/total bytes
      └─ 5-second safety timeout

7. Finalize (stateQueue → main)

connectionPhase = .ready                   // ☆ SENSOR IS READY
refreshBattery()
refreshSyncStatus()                        // device.isSynced() → sessionSynced
refreshRecordingStatus()
notify()                                   // push all state to UI

Sensor now appears in the UI with green indicator, battery percentage, and storage bar. Proceed to Sync & Record for the next steps.

Connection Queue

The connection queue ensures only one BLE connection attempt happens at a time. The SDK can't reliably handle concurrent connect() calls.

State (lives in DotRegistry, accessed on stateQueue)

var connectQueue: [String]       // FIFO array of UUIDs waiting to connect
var connectInProgress: String?   // UUID currently being connected (nil = idle)

Flow

1. User taps Connect → connectByUuid(_:)

connectByUuid(uuid)
    └─ stateQueue.async
        ├─ Guard: uuid exists in registry.byUuid
        ├─ Guard: not a duplicate (uuid not already in connectQueue or connectInProgress)
        ├─ registry.setConnectionPhase(uuid, .connecting)
        ├─ registry.connectQueue.append(uuid)
        ├─ startConnectTimer(uuid)   // 10-second timeout on main thread
        ├─ notify()
        └─ processConnectQueue()

2. processConnectQueue() dequeues one device

processConnectQueue()
    └─ stateQueue (already on it)
        ├─ device = registry.dequeueNextConnection()
        │     ├─ Guard: connectInProgress == nil (no active connection)
        │     ├─ Guard: !syncInProgress (sync blocks connections)
        │     ├─ Find first UUID in connectQueue that exists in byUuid
        │     ├─ Remove from connectQueue
        │     ├─ Set connectInProgress = uuid
        │     └─ Return device
        │
        ├─ if device == nil → return (queue empty or blocked)
        │
        └─ sdkQueue.async {
               DotConnectionManager.connect(device)
           }

3. Connection succeeds or fails → advance queue

Both onDeviceConnectSucceeded and onDeviceConnectFailed call advanceConnectQueue():

advanceConnectQueue()
    └─ stateQueue (already on it)
        ├─ registry.connectInProgress = nil
        └─ processConnectQueue()   // try next in queue

4. Timeout (10 seconds, no SDK callback)

startConnectTimer(uuid) creates a DispatchWorkItem scheduled on main thread. If it fires:

  • Sets connection phase to .failed("Connection timed out")
  • Calls advanceConnectQueue() to move on

If the SDK callback arrives before timeout, the timer is cancelled via connectTimers[uuid]?.cancel().

Why One at a Time

The Movella SDK's DotConnectionManager.connect() uses shared internal state. Calling it for device B while device A's connection is in-flight can cause A's callback to never fire or fire with B's device reference. The serial queue pattern avoids this entirely.

Reconnect Logic

onDeviceConnectSucceeded handles four distinct connection scenarios, each with different initialization paths. All non-sync paths call resetEraseState(dot) — an extracted helper that installs the onEraseStateChanged callback and clears erase flags (isErasing, isErasingFromPreviousSession, flashCorrupted). This was previously duplicated inline in each path.

Entry Point: onDeviceConnectSucceeded(_ device: DotDevice)

Everything below runs on stateQueue:

func onDeviceConnectSucceeded(_ device: DotDevice) {
    stateQueue.async {
        cancelConnectTimer(device.uuid)

        // PATH 1: Sync reconnect
        // SDK internally reconnects during sync. Lightweight update only.
        if registry.syncInProgress && registry.syncingUuids.contains(uuid) {
            registry.recordReconnection(device)
            return  // No init, no phase change, no notify
        }

        // PATH 2: Queued-but-not-active
        // SDK auto-reconnected before we dequeued this UUID.
        // Remove from queue (do NOT advanceConnectQueue — it wasn't connectInProgress).
        if registry.connectQueue.contains(uuid)
            && registry.connectInProgress != uuid {
            registry.connectQueue.removeAll { $0 == uuid }
            registry.recordReconnection(device)
            registry.setConnectionPhase(uuid, .initializing)
            sdkQueue.async { DotDevicePool.bindDevice(device) }
            initializeAfterConnect(dot: dot)
            return
        }

        // PATH 3: Auto-reconnect
        // Previously connected (dot exists), not in queue, not in progress.
        let isAutoReconnect = registry.byUuid[uuid]?.dot != nil
            && registry.connectInProgress != uuid
            && !registry.connectQueue.contains(uuid)
        if isAutoReconnect {
            registry.recordReconnection(device)
            registry.setConnectionPhase(uuid, .initializing)
            sdkQueue.async { DotDevicePool.bindDevice(device) }
            initializeAfterConnect(dot: dot)
            return
        }

        // PATH 4: Normal queue connection / BT-reset reconnect
        // Device at head of queue (connectInProgress == uuid).
        // If reconnecting (dot already exists), add 2s settle delay.
        let isReconnect = registry.byUuid[uuid]?.dot != nil
        let settleDelay: TimeInterval = isReconnect ? 2.0 : 0
        registry.recordConnection(device)  // creates Dot if first time
        sdkQueue.async { DotDevicePool.bindDevice(device) }
        initializeAfterConnect(dot: dot, settleDelay: settleDelay)
        registry.advanceConnectQueue(expect: device.uuid)  // safe version
        processConnectQueue()
        notify()
    }
}

Key detail: Path 4 uses advanceConnectQueue(expect: device.uuid) which only clears connectInProgress if it matches the expected UUID. This guards against the race condition where a different device connects while this UUID is connectInProgress (see Flash Recovery for the original bug).

initializeAfterConnect(dot:settleDelay:)

Takes a Dot (not a UUID) and decides whether to query flash storage or skip straight to .ready:

private func initializeAfterConnect(dot: Dot, settleDelay: TimeInterval = 0) {
    let uuid = dot.address

    dot.checkSensorActivity { [weak self] activity in
        guard let self else { return }
        self.stateQueue.async {
            switch activity {
            case .recording:
                // Sensor is mid-recording — skip flash query (it won't respond)
                self.registry.initializationInProgress.remove(uuid)
                self.registry.setConnectionPhase(uuid, .ready)
                dot.refreshSyncStatus()

                // Restore runner phase inline (no separate function)
                if let runner = RunnerStore.shared.runner(forSensorUuid: uuid) {
                    let phase = self.runnerPhasesInternal[runner.id] ?? .idle
                    if phase == .idle || phase.isError {
                        self.setPhase(.recording, forRunner: runner.id)
                    }
                }
                self.notify()

            case .erasing:
                // Sensor is mid-erase — skip flash, start polling
                self.registry.initializationInProgress.remove(uuid)
                self.registry.setConnectionPhase(uuid, .ready)
                dot.refreshSyncStatus()
                dot.refreshBattery()
                setOnMain { dot.isErasingFromPreviousSession = true }
                dot.startErasePollFromManager()
                self.notify()

            case .idle:
                // Safe to query flash
                self.refreshStorage(dots: [dot], settleDelay: settleDelay)
            }
        }
    }
}

checkSensorActivity (on Dot): Uses three racing paths to determine recording/erasing/idle state. First to complete wins via a hasCompleted flag:

  1. One-shot callback — installs recordingStatusCompletion, then calls device.getRecordingStatus() on sdkQueue. Fastest path (~0.3s) when the SDK fires the callback. Works on new device objects; silently broken on reused objects.
  2. Property polling loop — polls device.recording.recordingStatus every 0.3s for up to 2.5s. Catches reused device objects where the SDK updates the property without firing the callback (~0.6–1s). Trusts .isRecording and .isErasing immediately (non-default values). Only trusts .isIdle after 1s (the default value 0 could be uninitialized).
  3. 3-second timeout — assumes idle. Safety net for edge cases where both callback and property are unresponsive.

Flash Timeout Recovery

If checkSensorActivity returns .idle but the sensor is actually recording (SDK was too slow to populate the property), refreshStorage calls getFlashInfo which times out (the SDK won't respond during recording). The timeout handler in refreshStorage checks recordingStatus as a fallback:

  • .isRecording: Sensor recovers to .ready with recording phase restoration — looks up the runner via RunnerStore and sets its phase to .recording if idle/error. Self-healing for the app-relaunch scenario.
  • .isErasing: Sensor recovers to .ready with isErasingFromPreviousSession = true and starts erase polling. See Flash Recovery.
  • Other (genuine failure): Connection phase set to .failed("Initialization timed out").

refreshStorage: Delegates to DotOperationRunner.refreshStorage() which calls dot.getFlashInfo() for each UUID. On completion, marks the dot .ready and calls notify().

restoreRecordingPhase(for: uuid)

When a reconnected sensor is still recording, this method looks up which runner owns that sensor (via RunnerStore) and sets that runner's phase to .recording if it isn't already. This restores the UI without any persistence file — the sensor's own isRecording state is the source of truth.

The Settle Delay

After a Bluetooth power-off/reset, iOS reconnects devices but the SDK's internal BLE handshake isn't fully complete when onDeviceConnectSucceeded fires. bindDevice() returns immediately and device.isInitialized reports true, but getFlashInfo() never gets a callback because the underlying GATT services aren't ready.

The 2-second settleDelay (passed through to DotOperationRunner.waitForInitialization) adds a pause after isInitialized returns true but before calling getFlashInfo(). This gives the SDK time to finish its internal re-initialization.

Bluetooth Power-Off Recovery

When Bluetooth powers off or resets, onManagerStateUpdate fires with .poweredOff or .resetting:

Power Off / Reset

  • cancelAllConnectTimers() — cancel all pending timeout work items
  • registry.clearBusyFlags() — wipes connectInProgress, initializationInProgress, syncInProgress, syncingUuids, isScanningInternal
  • registry.markAllDisconnected() — sets every UUID's phase to .idle
  • All active runner phases are moved to .error("Bluetooth disconnected.")

Power On

  • Re-queues all previouslyConnectedUuids into connectQueue (skipping duplicates)
  • Starts connect timers for every queued UUID (prevents silent connect failures from blocking the queue)
  • Calls processConnectQueue() using persisted DotDevice references from byUuid immediately — no need to wait for discovery
  • Starts scan as a fallback in case stored device references are stale

Known limitation: If BT powers off during a sync, clearBusyFlags() resets syncInProgress and syncingUuids. But performSync’s SDK completion closure is still in flight with captured pre-reset data. If the closure fires after the reset, it dispatches back to stateQueue and could re-set syncInProgress or modify cleared state. See Vulnerabilities & Known Limitations #5.
